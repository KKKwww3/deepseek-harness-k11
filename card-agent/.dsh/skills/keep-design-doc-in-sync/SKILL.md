# 设计文档同步规则

关键要求：**需求或实现一旦变化，必须同步更新权威设计文档**。设计文档是团队与未来 Agent
的事实来源，绝不能长期落后于实际和已确认的需求。

## 何时触发

- 需求变化 / 新增决策点后
- 实现与文档出现偏差时（文档写了的机制代码里没有、或代码行为与文档不同）
- 完成一轮需求确认后，用户要求更新文档
- 开始新项目，需要把这套同步规则沉淀为 skill

## 执行步骤

1. **确认权威文档位置**：通常为项目 `README.md`（或约定的 `design.md`），开头明确标注
   「本文档是权威设计文档」。若尚无权威文档，创建它并标注。
2. **读取当前磁盘上的真实状态**：不能基于对话记忆或旧缓存，必须重新读取文件确认实际
   内容与实现（如运行 `git status`、`Read` 目标文件、`Glob` 目录结构）。
3. **逐项核对文档与需求/实现**：
   - 已确认且实际存在的 → 保留并可标注「已实现」
   - 已确认但尚未实现的 → 写入文档（如实描述，区分「已实现」/「规划」）
   - 文档写了但实际没有 / 代码行为不同 → 修正文档或修正实现
4. **更新文档**：保持结构清晰，补充新增决策点（忘记这项时），删除过时描述。
5. **收尾核对**：文档里的每个「现状」都能在磁盘实现上找到依据，不凭空描述。

## 纪律

- **不要相信记忆，以磁盘为准**：引用文件必须重新 Read。工具调用成功不代表已落盘，
  需用 `LS`/`Glob`/第二次 `Read` 复核。
- **区分「已实现」与「规划」**：未落盘的决策记入文档时明确标注，避免误导。
- **文档 ≠ 聊天记录**：只沉淀可复用的持久决策，不搬抄对话原文。
- **跨项目复用**：把此 skill（整个目录）复制到新项目 `.dsh/skills/keep-design-doc-in-sync/`。
